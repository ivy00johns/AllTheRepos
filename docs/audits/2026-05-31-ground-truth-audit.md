## main-ipc-security (Electron main process core — window management, IPC routing, security baseline)

**Status:** `complete`  ·  **Confidence:** high

**Maps to:** NEW-PLAN.md §3.1 process model, §3.3 IPC contract pattern, §3.4 security baseline. Spans Phase 0 (IPC ping + security defaults), Phase 1/2 (catalog/scan/git/settings/groups/app namespaces), Phase 3a (process/launcher), Phase 3b (claude). Contracts: contracts/ipc.v3b.md, contracts/ipc.v3.md.

**What works (verified in code):**
- Type-safe IPC bridge is real and fully wired. The IPC channel registry (src/shared/ipc.ts) defines all namespaces as `as const` literals. The preload (src/preload/api.ts) exposes exactly 41 ipcRenderer.invoke channels, every one referencing an IPC.* constant — grep for inline string channels returned NONE. Main has exactly 41 real `ipcMain.handle(` call sites, all using IPC.* constants — a clean 1:1 match with the preload surface.
- Preload exposes only the allowlisted surface: src/preload/index.ts does a single `contextBridge.exposeInMainWorld(PRELOAD_BRIDGE_KEY='atr', api)` and nothing else. `ipcRenderer` is never exposed; the `on*` event subscribers wrap on/off and return unsubscribe lambdas so raw ipcRenderer never reaches the renderer (api.ts:159-167, 332-345, 435-448).
- contextIsolation/nodeIntegration/sandbox/webSecurity are actually enforced in code (not just docs) for ALL THREE window factories: main-window.ts:62-70, spotlight.ts:84-88, tray-popover.ts:95-99 each set contextIsolation:true, nodeIntegration:false, sandbox:true, webSecurity:true, preload: out/preload/index.cjs.
- CSP is enforced via session.defaultSession.webRequest.onHeadersReceived (csp.ts:55-68), installed first in app.whenReady() before any window is created (index.ts:117). It strips any upstream CSP and sets default-src 'self'; script-src 'self' (prod); style-src 'self' 'unsafe-inline'; img-src incl avatars.githubusercontent.com; connect-src self + localhost:11434 + api.openai.com; object-src 'none'; base-uri 'self'; frame-ancestors 'none'. Matches §3.4 and adds hardening beyond the plan text.
- shell.openExternal allowlist is real (allowlist.ts): isUrlAllowed parses URL and checks ALLOWED_EXTERNAL_SCHEMES; openExternalAllowlisted returns a discriminated {ok,reason} and is the only path. setWindowOpenHandler (main-window.ts:79-84) and will-navigate (88-101) both gate through it and deny in-page navigation away from the renderer origin.
- Frame-origin check is wired on every handler. Every handler body calls assertRendererFrame(event) as its first statement (verified per-file: app=5/5, catalog=6/6, claude=7/7+, git=3/3, groups=5/5, launcher=6/6, process=3/3+, scan=3/3, settings=2/2, system=1/1). Verified directly in system.ts:88-91 and claude.ts:122-185.
- Every handler Zod-parses input AND output. claude.ts handlers parse input via <X>InputSchema.parse(raw) and parse the return via <X>ResultSchema.parse(result) before returning; system.ts parses both PingInputSchema and PingResponseSchema. All Phase 3b schemas exist in src/shared/schemas.ts (ClaudeRepoStateInputSchema:855, ClaudeGlobalUsageResultSchema:889, ClaudeLaunchInputSchema:919, etc.).
- Main process lifecycle is fully implemented (index.ts): single-instance lock (99), second-instance focus, ordered boot (CSP -> protocol -> legacy migration -> drizzle migrations -> scan/process/launcher/claude service boot -> registerIpcHandlers -> event fan-out subscriptions -> window -> tray -> hotkey), macOS activate/window-all-closed/before-quit handlers, and three webContents.send broadcast fns (scan/process/claude) defensive against destroyed windows.
- The main+preload+shared TypeScript project (tsconfig.node.json, which includes src/main, src/preload, src/shared) typechecks clean: `tsc --noEmit -p tsconfig.node.json` exits 0. electron.vite.config.ts emits preload as CJS to out/preload/index.cjs — exactly the path the window factories load.
- register.ts orchestrates all 10 namespace registrars in one place; handlers do not self-register at import time, and each registrar removeHandler()s before re-registering for hot-reload idempotency.

**Stubbed / missing:**
- catalog:smartFilter channel is wired through the full IPC/preload surface but is explicitly a Phase 4 feature whose contract is 'locked now' (ipc.ts:50) — the channel exists but the underlying intelligence is out of scope for Phase 3b (not a main-ipc-security defect, just noted as a present-but-forward-dated channel).
- No runtime/integration test exercises the production Electron build's frame-origin rejection or non-allowlisted file:// URL rejection — qa-report security note (score 4) admits the production Electron build is 'still not automated-tested for non-allowlisted file:// URL rejection (carried over from earlier phases).' The frame check and allowlist are unit-testable pure functions but the wired end-to-end enforcement is unverified by E2E because the Electron E2E suite cannot run in the build environment (Node 21.2.0 vs @electron/rebuild needing Node 22).

**Discrepancies (claim vs reality):**
- Frame-origin check is weaker than the §3.4 contract implies. §3.4 says 'Every ipcMain.handle validates event.senderFrame.url to make sure the request came from your own renderer.' The implementation (system.ts:28-41 and _frame.ts:16-28) returns TRUE for frameUrl === '' OR 'about:blank'. A null/empty senderFrame.url therefore passes the check. The code comments justify this as 'renderer is initializing', but it is a genuine relaxation of the documented guarantee — an attacker frame with an empty URL would not be rejected. qa-report's security note (score 4) does not mention this allowance.
- Duplicated frame-check logic in two files (src/main/ipc/system.ts assertRendererFrame and src/main/ipc/_frame.ts assertRendererFrame) with identical bodies. _frame.ts's own comment flags this: 'Both copies MUST stay in lockstep ... until a future cleanup unifies them.' They are currently in sync, but this is a known duplication/maintenance hazard, not a single source of truth.
- src/preload/index.d.ts doc comment only documents the 'Phase 2 surface' (system/catalog/scan/git/settings/groups/app) and omits process/launcher/claude. The TYPE is correct (it is `typeof api` via AtrApi, so the real renderer typings DO include the Phase 3a/3b namespaces) — but the doc comment is stale relative to the code, a docs-vs-code drift.
- package.json scripts `dev`/`build`/`start`/`lint` still point at Next.js (`next dev`/`next build`/`next start`/`next lint`) and next ^16 + next.config.ts are still present. The Electron toolchain lives under separate electron:* scripts (electron-vite). This is expected mid-migration but means the default `build` command does NOT build the Electron app — a footgun for anyone running `npm run build` expecting the desktop app.
- qa-report.json status 'phase-3b-claude-integration-complete' with gate_decision.proceed=true is accurate for the unit/contract layer of this subsystem (IPC wiring, schemas, frame checks all real and typecheck-clean), but the 'complete' framing rests on a green UNIT suite while the E2E/Electron-runtime layer is admittedly un-executed (blockers list cites the Node 21 / @electron/rebuild issue). So end-to-end runtime enforcement of the security baseline is asserted but not machine-verified.

**Risks:**
- Empty/about:blank senderFrame.url bypass in the frame-origin check is the single most material security gap — it narrows the §3.4 'every handler validates the sender frame' guarantee. If a sandboxed sub-frame or an early-load context can present an empty frame URL, it would clear the gate.
- Frame-check logic duplicated across system.ts and _frame.ts can drift; a future tightening applied to one and not the other would silently leave half the handlers on the weaker policy.
- Security enforcement (frame check + openExternal allowlist + CSP) is only proven at the unit level; the Electron E2E layer that would prove enforcement against a real renderer/file:// origin cannot run in the current environment, so a regression in window webPreferences or CSP installation ordering would not be caught by the existing automated suite.
- Stale package.json `build`/`dev` scripts pointing at Next.js risk a developer or CI building the wrong app (legacy localhost bundle) and believing they shipped the Electron app.

**Recommended next steps:**
- Tighten assertRendererFrame: reject empty/about:blank senderFrame.url, or at minimum gate the allowance to dev-only (process.env.ELECTRON_RENDERER_URL set). Update §3.4 contract text and qa-report security note to match whichever policy is chosen.
- Unify the duplicated assertRendererFrame into a single shared helper (e.g. keep _frame.ts as the source of truth and have system.ts import it) to eliminate the lockstep hazard.
- Add an Electron E2E or integration test that asserts: (a) a foreign/empty frame is rejected, (b) a non-allowlisted file:// or javascript: URL is denied by openExternalAllowlisted, (c) the CSP header is present on the first document response. This closes the 'enforcement proven only at unit layer' gap. Resolve the Node 21 / @electron/rebuild blocker first (pin Node 22+ in CI per qa-report recommendation).
- Refresh src/preload/index.d.ts doc comment to list the process/launcher/claude namespaces so docs track the code.
- Rename or repoint the legacy Next.js package.json scripts (build/dev/start/lint) once feature parity is confirmed, so the default build targets the Electron app — avoids shipping the wrong artifact.
